# 终端渲染错乱修复设计

## 概述

当前问题表现为：通过 `server` 直接托管的生产前端页面访问网页终端时，在输出达到一定行数后，新行会显示到上方并与已有内容重叠；远端 Windows 上的真实终端输出正常，问题仅发生在浏览器中的终端渲染层。

本次修复只针对前端 `xterm.js` 初始化配置，目标是在不改变后端 PTY、WebSocket 协议和会话管理逻辑的前提下，修复大量纯文本输出时的换行显示异常。

## 问题边界

- 异常仅发生在网页终端显示层
- 远端 Git Bash / PTY 输出本身正常
- 通过 `server/index.js` 托管的 `client/dist` 生产构建页面访问时可复现
- 纯文本大量输出也会触发，不依赖颜色、高级 ANSI 控制序列或全屏程序

这说明问题优先落在前端终端渲染兼容，而不是后端 shell 或数据传输。

## 根因假设

`client/src/views/Terminal.vue` 在创建 `xterm` 实例时只配置了主题、字体和光标行为，没有启用换行兼容选项。

在当前 Windows/Git Bash/浏览器终端链路下，前端收到的数据流中可能存在只携带 `\n`、未被正确按 `\r\n` 语义处理的情况。这样在大量输出时，xterm 的光标移动与行首回退可能不一致，导致后续内容绘制到错误位置，视觉上表现为新行覆盖旧内容或上下重叠。

这是当前最符合症状且改动范围最小的根因假设。

## 设计方案

### 推荐方案：最小显示层修复

只修改 `client/src/views/Terminal.vue` 中 `new Terminal(...)` 的初始化配置，增加：

- `convertEol: true`

作用：让前端在处理收到的 `\n` 时按 `\r\n` 的效果移动光标，即进入下一行并回到行首。

这样可以在不修改后端输出格式的前提下，修正浏览器端的换行渲染行为。

### 暂不采用的方案

#### 1. 立即启用 `windowsMode`

不作为第一刀修复。原因：

- `windowsMode` 在当前 xterm 类型定义中已标记为 deprecated
- 它会引入额外的 Windows 包裹/重排启发式，不适合在证据不足时直接开启
- 当前问题更像基础换行处理异常，优先用更小、更直接的 `convertEol` 修复

#### 2. 修改后端输出或协议

暂不修改 `server/terminal.js` 或 WebSocket 消息结构。原因：

- 当前证据不支持后端 PTY 输出错误
- 修改协议会扩大影响面，增加回归风险
- 现阶段应先修复明确落在显示层的问题

#### 3. 同时做布局重构

暂不在第一轮中调整 `App.vue`、终端容器高度或滚动布局。若最小修复后问题仍存在，再进入第二轮设计排查视口尺寸和画布重排问题。

## 实施范围

### 修改文件

- `client/src/views/Terminal.vue`

### 不修改文件

- `server/terminal.js`
- `server/index.js`
- WebSocket 协议
- 其他终端 tab 管理逻辑

## 验证方案

仓库当前未配置自动化测试框架，因此本次验证采用最小人工复现流程：

1. 重新构建前端产物
2. 通过 `server` 启动生产服务并访问页面
3. 在网页终端执行纯文本大量输出命令，例如：
   - `seq 1 200`
   - `for i in {1..200}; do echo $i; done`
4. 确认输出是否仍出现新行覆盖旧内容、上下混叠或看不到真实内容
5. 再做普通交互检查：
   - 正常输入命令
   - 回车执行
   - 滚动查看历史输出
   - 多 tab 切换后终端仍可正常显示

## 失败后的下一步

如果 `convertEol: true` 后问题仍存在，则下一轮应优先进入更精确的 Windows PTY 兼容方案，而不是继续叠加猜测性修改。下一步候选方向为：

- 基于平台信息评估是否改用 `windowsPty` 配置
- 检查终端容器尺寸变化和 `fit()` 时机
- 必要时增加最小诊断日志确认收到的数据换行形式

## 非目标

- 不重构终端页面结构
- 不修改终端会话生命周期
- 不优化 ANSI 控制序列兼容以外的显示问题
- 不引入测试框架或额外基础设施
